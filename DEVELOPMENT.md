# Развитие CYBERLAB

Текущий код — рабочий прототип **0.1.0**. **CYBERLAB 1.0 — цель разработки**,
а не уже выпущенная версия. Основная платформа 1.0 — Windows 10/11;
совместимость логики и интерфейса с Linux сохраняем.

Проект также нужен для обучения Python. Каждая новая возможность должна оставаться
объяснимой автором: что получает функция, какой алгоритм выполняет и что возвращает.
Маршрут изучения и упражнения находятся в [STUDY_GUIDE.md](STUDY_GUIDE.md).

## Что реализовано

| Часть | Реальное состояние |
| --- | --- |
| Главное окно | PySide6: панели, показатели, дерево решений и сворачиваемое сравнение |
| Виртуальный ПК | Учебные почта, файлы, журнал и макет браузера без действий с настоящей системой |
| Сценарий | `phishing-v1`: восемь маршрутов к четырём итогам |
| Возврат к решению | Загрузка снимка любого сохранённого шага и продолжение от него |
| Альтернативные ветки | Прежние последствия сохраняются; повтор того же выбора не создаёт дубликата |
| Сравнение | Пять показателей двух любых снимков, независимо от активного шага |
| Хранение | SQLite v1: снимки, родители, активный указатель; транзакции и восстановление |
| Наставник | Локальные объяснения снимка и различий A/B через `mentor.py`, без AI-модели |
| Разделение кода | Модель, сценарии, сессия, SQLite, UI, виртуальный ПК, стили и наставник отдельно |
| Проверки | Модель, история, UI, наставник и запускаемые примеры учебного руководства |
| Поставка | Python-пакет, `uv.lock`, инструкция запуска, workflow Windows/Ubuntu |

## Что пока не реализовано

- Меню выбора нескольких сценариев и редактор сценариев. Модель уже принимает
  другой `Scenario`, но в поставке один; макет виртуального ПК связан с фишингом.
- Генеративный AI-наставник, чат с моделью и API. Вместо заглушек работают локальные
  объяснения; никаких фиктивных ответов сервиса или выдуманных API-ключей нет.
- Установщик Windows и проверенный запуск без отдельно установленного Python.
- Подтверждённая проверка на реальных Windows 10 и 11, включая масштабирование дисплея.
  Workflow на `windows-latest` полезен, но не равен двум таким проверкам.
- Экспорт отчёта для защиты, выбор старых тренировок в окне и профили учеников.
- Миграции для будущих схем БД. Сейчас поддерживается v1; более новая отвергается
  без перезаписи. Сбрасывать базу вместо миграции нельзя.
- Совместное редактирование одной базы несколькими процессами, сложные сетевые
  лаборатории и запуск настоящих вредоносных программ.

## Как развивать приложение небольшими шагами

### Этап 1. Понять и закрепить текущие алгоритмы

Пройти руководство: найти последствия выбора, изменить учебную копию сценария,
добавить одно действие и проверить его тестом. Затем объяснить дерево снимков,
возврат, транзакцию и сравнение своими словами.

Готово, когда автор может без подсказки показать эти места в коде, а все прежние
проверки продолжают проходить.

### Этап 2. Проверить Windows 10/11

Запустить текущий пакет на обеих версиях Windows. Проверить установку зависимостей,
русский текст, путь профиля с кириллицей, масштаб 100/125/150 %, окно 1120×720,
клавиатуру, создание веток и перезапуск с той же SQLite. Записать реальные результаты
в `docs/validation.md`, отдельно от Linux и CI. Linux-тесты оставить в workflow.

Готово, когда оба запуска подтверждены, известные проблемы описаны и функционал
не зависит от Windows-путей в коде модели.

### Этап 3. Добавить второй сценарий и выбор в окне

Сначала описать небольшой `Scenario` и проверить его переходы без Qt. Затем
добавить выбор сценария и нужное содержимое виртуального ПК. Старый `phishing-v1`
оставить доступным; чужие истории нельзя смешивать.

Использовать простые функции, классы и список сценариев. Подключаемая система
плагинов или сервер для двух сценариев пока не нужны.

### Этап 4. Подготовить отчёт для защиты

Добавить экспорт выбранных веток: решения, значения до/после и различия.
Для начала достаточно текстового файла через диалог сохранения. Отчёт должен
формироваться из настоящих снимков, а не из заранее подготовленного текста.

### Этап 5. Подключить настоящий AI-наставник, если он нужен

Сначала определить, что он объясняет сверх локальных правил. Выбрать модель
и способ запуска: локальная модель или внешний сервис. Текущий `mentor.py`
сохранить как независимую локальную функцию и резерв при отсутствии связи.
Клиент выбранного сервиса вынести в отдельный `ai_mentor.py` **когда появится
реальная реализация**, а не добавлять сейчас пустой класс.

Модель должна получать только данные учебной симуляции. Она не изменяет снимки,
оценку риска или записи SQLite. Понадобятся фоновые запросы без зависания окна,
тайм-ауты, понятные ошибки и тесты недоступности сервиса. Ключи не хранятся в Git.
Генерируемый ответ нельзя выдавать за гарантированную оценку безопасности.

### Этап 6. Подготовить выпуск 1.0 для Windows

После стабилизации выбрать инструмент упаковки и собрать приложение на Windows.
Проверить его на машине без Python, убедиться в сохранении истории при обновлении
и повторить основные пользовательские маршруты. Только после этого менять номер
версии на 1.0. Linux остаётся поддерживаемой архитектурой с отдельными проверками.

## Правила изменений

1. Одна задача — небольшое понятное изменение. Не заменять работающую механику заглушкой.
2. Правила последствий менять в сценариях/модели, SQL — в хранилище, отображение — в UI.
3. Для изменения правил опубликованного сценария использовать новый `scenario.id`:
   уже сохранённые снимки не пересчитываются автоматически.
4. Изменение формата снимка или таблиц требует плана миграции и теста старой базы.
5. Сохранять параметры API, которыми пользуются существующие части приложения,
   если нет отдельной причины их менять.
6. Комментировать причину сложного решения по-русски, а не пересказывать очевидную строку.
7. После каждой существенной группы правок выполнять тесты. Новое действие — новый тест;
   нельзя ослаблять старые утверждения только ради зелёного результата.

Из корня репозитория, одинаково в PowerShell и Bash:

```sh
uv sync --locked
uv run --locked pytest
uv run --locked ruff check .
uv run --locked ruff format --check .
uv build
```

В облаке без экрана тесты выбирают `offscreen`. Это проверяет Qt, но не заменяет
ручную проверку рабочего стола Windows. Команда `uv run --locked cyberlab`
нужна для обычного графического запуска; отдельную историю можно задать
через `--database ./practice.sqlite3`.

## Подготовка к GitHub

Проверить `git diff`, выполнить проверки и создать небольшой коммит с описанием
результата. Убедиться, что в нём нет `.venv`, SQLite и личных данных. Отправлять
без принудительного переписывания истории. Для обсуждения крупных изменений
использовать отдельную ветку и Pull Request. Созданный локальный коммит, отправка
на GitHub и успешный запуск CI — три отдельных результата; отмечать их по факту.
